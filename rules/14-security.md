# セキュリティ方式

> 常時適用

## 前提

- MCP サーバの利用者は 1 人とする。
- 想定する MCP クライアントは、Claude（claude.ai・Claude Desktop・Claude モバイルアプリ）、Claude Code、Microsoft 365 Copilot（Copilot Studio）である。いずれも OAuth 2.0 で MCP サーバに接続できるため、MCP クライアントの認証は OAuth に一本化する。
- MCP サーバは、接続先（サイト。`rules/13-webapp-api.md`）ごとに Web アプリの API キーを保持し、自身が Web アプリの API を呼ぶ。MCP クライアントから受け取ったトークンを、Web アプリへ渡さない（トークンのパススルーをしない）。

## 通信

- 開発環境では http を用いてよい。待ち受けは `127.0.0.1` に限る。
- 本番環境では https を用いる（nginx で TLS を終端する。`rules/17-deploy.md`）。MCP クライアントはインターネット上（Anthropic や Microsoft のクラウド）から接続するため、公開 URL はインターネットから届く https とする。
- Web アプリの API も、本番では https の URL で呼ぶ。

## MCP クライアントの認証（組み込みの OAuth 認可サーバ）

MCP サーバは、MCP の認可仕様に従う OAuth 2.1 の保護リソースであり、同じプロセスの中に、利用者 1 人向けの最小限の認可サーバを持つ。外部の ID 基盤は使わない。

### 対応する仕様

- 認可コードフロー＋PKCE（`S256` のみ。`plain` は受け付けない）
- 動的クライアント登録（DCR。RFC 7591）
- 保護リソースメタデータ（RFC 9728。`/.well-known/oauth-protected-resource`）
- 認可サーバメタデータ（RFC 8414。`/.well-known/oauth-authorization-server`）。`code_challenge_methods_supported` に `S256` を載せる
- リソースインジケータ（RFC 8707）。トークンは MCP サーバの公開 URL（`MCP_PUBLIC_URL`）向けに発行し、アクセストークンの受け取り時に対象を確かめる。別の宛先向けのトークンは受け付けない
- リフレッシュトークンのローテーション（使うたびに新しいリフレッシュトークンを発行し、古いものを無効にする）。無効なリフレッシュトークンには `invalid_grant` を返す
- クライアントクレデンシャルズ（`client_credentials`）など、利用者を介さないフローは提供しない

公式 Python SDK の認可サーバの仕組みを使い、プロトコルの処理を自前で実装しない。

### 未認証の要求

- アクセストークンが無い・無効・期限切れ・対象違いの要求は、HTTP 401 で拒否し、`WWW-Authenticate: Bearer resource_metadata="<保護リソースメタデータの URL>"` を付ける。ツールは実行しない。

### クライアントの登録とリダイレクト URI

- DCR で登録を受け付けるが、登録できるリダイレクト URI は、許可リスト（`MCP_ALLOWED_REDIRECT_URIS`）に一致するものに限る。許可リストに無いリダイレクト URI での登録は拒否する。
- 許可リストの既定値は、利用するクライアントのものとし、設計（`design.md`）に列挙する。
  - Claude（Web・Desktop・モバイル）: `https://claude.ai/api/mcp/auth_callback`
  - Claude Code: `http://localhost/callback`、`http://127.0.0.1/callback`（ポート番号は問わずに照合する）
  - Microsoft 365 Copilot: Copilot Studio が示すリダイレクト URI
- 許可リストの照合は完全一致とする（ループバックのポート番号だけを例外とする）。

### サインイン画面

- 認可要求を受けると、MCP サーバはサインイン画面を表示する。利用者がパスフレーズを入力して許可したときだけ、認可コードを発行する。
- 画面には、要求しているクライアントの名前と、リダイレクト先のホスト名をはっきり示す。
- パスフレーズは、ハッシュ（`hashlib.scrypt` など、ソルト付きの低速なハッシュ）だけを `.env` に持つ（`MCP_SIGNIN_PASSPHRASE_HASH`）。平文を保存しない。比較は定数時間で行う。
- 総当たり対策として、サインインの失敗が一定回数（`MCP_SIGNIN_MAX_FAILURES`）続いたら、一定時間（`MCP_SIGNIN_LOCK_MINUTES`）すべてのサインインを受け付けない。
- サインイン画面は CSRF 対策（フォームごとの使い捨ての値）を行い、`X-Frame-Options: DENY` などでほかのサイトへの埋め込みを禁止する。
- 画面の作り方は `rules/12-server.md`。

### トークン

- アクセストークン・リフレッシュトークン・認可コードは、推測困難な乱数（32 バイト以上）とする。JWT は使わない。
- 保存するのは SHA-256 のハッシュだけとし、トークンそのものは保存しない（保存先は `rules/12-server.md`）。
- 有効期間は `.env` で設定する。
  - 認可コード: 短く（既定 5 分）。1 回だけ使える
  - アクセストークン: `MCP_ACCESS_TOKEN_TTL_MINUTES`
  - リフレッシュトークン: `MCP_REFRESH_TOKEN_TTL_DAYS`（0 は無期限）。値は設計で決める
- すべてのトークンとクライアント登録を失効させる手段を、運用コマンドとして用意する（端末を紛失したときのため）。失効後は、各クライアントで再接続（サインイン）が必要になる。

## Web アプリの API キーの保持

- Web アプリの API キーは、サイトごとに `server/.env` に置く（名前は `rules/13-webapp-api.md`）。`sites.toml` やコード、リポジトリには置かない。
- `server/.env` と、トークンの保存先は、MCP サーバを動かす OS ユーザだけが読めるようにする。
- API キーは、そのサイトの API 基点 URL（`sites.toml` に書いたもの）へだけ送る。他のサイト・他の宛先へ送らない。
- API キーを失効・入れ替えしたときは、`.env` を書き換えて MCP サーバを再起動する。

## 秘密情報の扱い

- パスフレーズ、アクセストークン、リフレッシュトークン、認可コード、クライアントシークレット、Web アプリの API キーを、ツールの出力・エラー文・ログ・URL（クエリ。ただし OAuth の仕様上 URL に載る認可コードと `state` を除く）に含めない。ログで Web アプリの API キーを識別するときは、先頭 12 文字だけを出す。
- サイトの一覧をツールで示すときも、名前と説明だけを出し、URL や API キーは出さない。
- Web アプリの API の応答に含まれるデータは利用者本人のものである。ログには識別子と件数だけを出し、本文（メモの内容など）は出さない。

## Origin と公開範囲

- MCP のエンドポイントでは `Origin` ヘッダを検証する（`rules/12-server.md`）。
- CORS は許可しない（ブラウザから直接 MCP のエンドポイントを呼ぶ要件は無い）。OAuth のメタデータなど、仕様上ブラウザから読まれうるものは設計で個別に決める。
- MCP クライアントは Anthropic や Microsoft のクラウドから接続するため、接続元の IP での制限は行わない（行う場合は、各社が公開する接続元の範囲を設計に書く）。

## 変更操作

- 登録・更新・削除を行うツールは、ツールの注釈で変更操作であることを示す（`rules/12-server.md`）。MCP クライアント側で利用者の確認を挟めるようにするため。
- 削除など元に戻せない操作のツールの説明には、元に戻せないことを明記する。
